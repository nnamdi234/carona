Domain

People and terms

"Carona" is Portuguese for a lift. One account can do both jobs: a person who books a seat on Monday might drive on Friday. So passenger and driver describe what someone is doing, not what kind of account they have.

Passenger
A signed-in user who searches for rides and books seats.
Driver
A user who has registered at least one vehicle and offers a ride with it.
Admin
Future role for support and moderation. This is what the role column should be for.
Vehicle
A car owned by a user: make, model, colour, plate number, and seat capacity. Passengers use the colour and plate to find the car at pickup.
Ride
One trip a driver offers: origin, destination, departure time, fare, and the vehicle used.
Booking
A passenger's claim on one or more seats of a ride. Not in the code yet.
Seats left
Seats offered minus seats in active bookings. Calculated, never stored.
Fare
The price of a ride. Whether it is per seat or for the whole trip is still open (see the questions at the end).

For the frontend

Talking to the API

Success: one envelope everywhere

{
  "success": true,
  "message": "vehicles retrieved successfully",
  "data": [ { "id": "3f2b…", "make": "Toyota", "model": "Corolla", "colour": "Silver",
              "capacity": 4, "plate_number": "LND-482-KJ", "owner_id": "a91c…",
              "created_at": "2026-11-02T09:14:22Z", "updated_at": "…", "deleted_at": null } ]
}

The frontend should read data and can show message as a toast. message is written for developers right now ("vehicle created successfully"), so the UI should keep its own copy for anything a person reads.

Errors: two shapes

Errors raised in the controllers have detail as a string. Errors from Pydantic validation (status 422) have detail as a list, one entry per invalid field. The frontend needs one helper that handles both and maps 422 entries onto the matching form fields.

// 400, 401, 403, 404 from HTTPException
{ "detail": "Vehicle already exists" }

// 422 from request validation
{ "detail": [ { "type": "string_too_short", "loc": ["body", "make"],
                "msg": "String should have at least 2 characters", "input": "K" } ] }

Auth

Sign inPOST /users/login with email and password, then read data.access_token.
Each requestSend the header Authorization: Bearer <token>.
Who am ICall GET /users/me after login and on app start. Don't rely on decoding the token in the browser.
Expiry24 hours. There is no refresh token, so the user signs in again.
Token rejectedExpired or invalid tokens return 401 with a readable message. Clear the token and go to sign-in.
No token sentFastAPI's HTTPBearer rejects the request before our code runs. Confirm the status code against the running server before you rely on it.
Before any browser can call the API

The app has no CORS middleware. A frontend served from another port, for example a Vite dev server on localhost:5173, will have every request blocked by the browser until CORSMiddleware is added in main.py.

Where it is heading

The API description already promises to "create and manage carpooling rides, view available rides, and join existing rides". Rides cover the first two. Joining needs a Booking table, which does not exist yet. Here is the smallest model that delivers the whole promise. New items are proposals for you to accept or change.

Recommended decisions

  • Being a driver is a capability, not a role.Anyone who owns a vehicle can offer a ride. Keep role for user and admin. The UI then shows "Offer a ride" to everyone and asks for a vehicle first if they don't have one.
  • Add seats_offered to Ride.A driver may not want to fill every seat. It must be at most the vehicle's capacity (less one if capacity counts the driver). Seats left is seats_offered minus seats in confirmed bookings, calculated when you read it.
  • Make driver_id and vehicle_id required.Both are nullable today, but a ride without a driver or a car can't be shown to passengers. The server should set the driver from the token and check the driver owns the vehicle.
  • Keep places as free text for version 1.Origin and destination stay as strings, for example "Ikeja City Mall". Map coordinates and search by distance can come later without changing the screens much.
  • Use instant booking for version 1.A booking is confirmed straight away if seats are left. Driver approval adds a pending state, notifications and another screen. Leave it for later.
  • Honour deleted_at.The column exists but no query filters on it. Pick soft delete or hard delete now so list screens don't show deleted cars.

Ride and booking lifecycles

Each state becomes a status badge in the design system, so the list of states needs to be fixed before the colours are.

Ride

stateDiagram-v2
  direction LR
  [*] --> scheduled : driver posts ride
  scheduled --> in_progress : driver starts trip
  scheduled --> cancelled : driver cancels
  in_progress --> completed : driver ends trip
  completed --> [*]
  cancelled --> [*]
MoveWhoRule
scheduled → in_progressDriverAllowed from a short time before departure, for example 30 minutes
scheduled → cancelledDriverAny time before starting. Every active booking is cancelled too.
in_progress → completedDriverConfirmed bookings become completed and can be rated

"Full" is not a state. It is shown when seats left is 0, and the ride stays scheduled.

  completed --> [*]

User journeys

Each step shows the endpoint behind it. These steps become the screen list in phase C.

Get started

  1. Create an accountLivePOST /users/register
  2. Sign inLivePOST /users/login
  3. Load my profileLiveGET /users/me

Manage my vehicles

  1. See my vehicles, or an empty state that prompts me to add oneLiveGET /vehicles/
  2. Add a vehicleLivePOST /vehicles/
  3. Edit a vehicleBrokenPATCH /vehicles/{id}
  4. Remove a vehiclePlannedDELETE /vehicles/{id}

Find and book a ride (passenger)

  1. Search by origin, destination and datePlannedGET /rides?origin=…&destination=…&date=…
  2. Compare results: time, fare, seats left, driverPlannedsame response
  3. Open ride details: car colour and plate, driver namePlannedGET /rides/{id}
  4. Book seatsPlannedPOST /rides/{id}/bookings
  5. See it under My trips, or cancel itPlannedGET /bookings/me · PATCH /bookings/{id}

Offer a ride (driver)

  1. Pick one of my vehicles, or add one firstLiveGET /vehicles/
  2. Enter route, departure time, seats, farePlannedPOST /rides
  3. See who bookedPlannedGET /rides/{id}/bookings
  4. Start, end or cancel the tripPlannedPATCH /rides/{id}/status

Your call

Open questions

These decide what some screens show. Where I've given a default, the designs will use it unless you say otherwise.

  1. Does vehicle capacity include the driver's seat?Default: no. Capacity means passenger seats.
  2. Is fare per seat or for the whole ride, and who sets it?Default: per seat, set by the driver.
  3. Where does distance_km come from? It is required, but a driver can't be expected to type it.Default: make it optional until maps arrive.
  4. Instant booking or driver approval?Default: instant for version 1.
  5. How late can a passenger cancel, and is there a penalty?Default: until departure, no penalty.
  6. Is payment handled in the app or in cash at pickup?Default: cash. The UI shows the amount but doesn't take payment.
  7. Which market and currency come first?The sample data uses Lagos places and naira (₦) until you say otherwise.
